Aurora MySQLからRedshift/Snowflake/S3へデータを転送したくて、OSSのELTツールを調べました。
候補に挙げたのは次の2つです。

- [Sling](https://github.com/slingdata-io/sling-cli)
- [dlt](https://github.com/dlt-hub/dlt)

# 前提と要件

- ニアリアルタイム同期は不要。日次・時間単位のバッチで足りる
- 個人情報を持つカラムをRedshift/Snowflake/S3に置かない
- もしくは、個人情報を可逆に暗号化する手段があるか

ニアリアルタイムを捨てられるかどうかは最初に確認しておいたほうがいいです。
秒単位の遅延が必要だとCDC(変更データキャプチャ)が前提になり、後述するようにここが有償の壁になります。

# コネクタの有無では差がつかない

必要だった経路は、両方とも対応していました。

| 経路 | Sling | dlt |
|------|-------|-----|
| MySQL → Redshift | ✅ S3経由のCOPY(`aws_bucket`が必須) | ✅ 既定はINSERT、S3 stagingは任意 |
| MySQL → Snowflake | ✅ | ✅ |
| MySQL → S3(Parquet) | ✅ | ✅ |
| MySQL → Iceberg / S3 Tables | ✅ | ✅ |

Slingは、30以上のデータベースと9つのクラウドストレージ、dltも同等の範囲をカバーしています。
違いがあるとすればRedshiftくらいでしょうか。
Slingは、接続設定に`aws_bucket`が必須で、バルクロード前提の割り切った設計になっています。
dltの方は、認証情報にS3が出てこなくて、`staging='filesystem'`を足したときだけS3を経由します。

Redshift自体がS3を要求しているわけではありません。
`COPY`コマンドの読み込み元がS3などに限られているだけで、普通の`INSERT`も受け付けます。

とは言え、dltのドキュメントには「`insert-values`は大きなINSERT文を生成するので、他の手段があるなら避けたほうがいい(遅いため)」と書かれています。
データ量が増えれば、結局どちらもS3経由に落ち着きそうです。

という訳で、ここから先は機能差の話になります。

# 無償で使える範囲は、両者でかなり違う

Slingは、**GPL-3.0**です。
CLIバイナリを社内でそのまま実行する分には「頒布」に当たらないのでソース公開義務は発生しませんし、AGPLと違ってネットワーク越しの提供にも公開義務はおよびません。
改変して社外に配布するようなことをしなければ、社内利用では実質的に制約なしと考えて良さそうです。

ただし、ライセンスより**プランの区切り**のほうが重要でした。

| プラン | 価格 | 含まれる機能 |
|--------|------|-------------|
| CLI(無償) | $0 | `full-refresh` / `truncate` / `incremental` / `snapshot` / `backfill` |
| CLI Pro | $79/月 | 削除検知(Capture Deletes)、並列処理、Staged Transforms、OpenTelemetry |
| CLI Pro Max | $149/月 | CDC(binlog/WAL)、Schema Migration |

削除検知がProで、CDCがPro Maxです。

一方のdltは、**Apache-2.0**です。
ただし、dlt Hubが提供するingestion toolkit(CDC相当のソース)は商用ライセンスです。

無償で使えるのはコアライブラリの範囲、具体的には`sql_database` source・各destination・merge戦略・`hard_delete`ヒントまでです。
フルロードと増分更新に限れば、これで足ります。

なお、組み合わせて使うdbtは、2026年6月にdbt FusionのコードがApache-2.0でdbt-coreリポジトリに統合され、これがdbt Core v2になりました。
以前ELv2だった部分もApache-2.0に移行しています。
ライセンスとしては、制約が緩む方向に動いているので、ここのリスクは低そうです。

# 物理削除をバッチでどう追いかけるか

今回、いちばん悩ましいのが物理削除です。

`sql_database`のようなcursorベースの増分抽出は、更新日時カラムの最大値を覚えておいて「その値より大きいレコード」を取ってくる方式です。
この方式だとソース側で物理削除された行は、単に**現れなくなる**だけで、削除されたという事実がどこにも現れません。
転送先には消えたはずの行が残り続けます。

Sling無償版でこれに対処する手段は、`full-refresh`か`truncate`で全件入れ替えるしかありません。
削除検知にあたるCapture DeletesはPro、binlogから削除イベントを拾うCDCはPro Maxです。
テーブルが小さいうちは、全件入れ替えで回せますが、データ量が増えると苦しくなります。

dltには、`hard_delete`というカラムヒントがあり、削除フラグを実際のDELETEに変換してくれます。

```python
columns={"deleted_at": {"hard_delete": True}}
```

bool型なら`True`の時だけ削除対象になり、それ以外の型なら`None`以外で削除されます。
ルートテーブルのレコードが削除されると、root keyを辿ってネストテーブルの対応レコードも消えます。

ただ、`hard_delete`が使えるのは、**ソースが削除を伝えてくれる場合だけ**です。
論理削除(削除フラグを立てる運用)なら素直に使えますが、物理削除そのものを検知してくれるわけではありません。
cursorベースの増分で取ってきたデータの中に、削除された行は最初から入っていないからです。

# dltの強みは、PK突合という逃げ道を自分で書けること

では、dltの場合は物理削除にどう追従するか。
`hard_delete`に流し込むデータを自分で作るという手が使えます。

1. 通常の増分ロードとは別に、主キーだけを抽出するリソースを定期実行する
2. 転送先の主キー一覧とanti-joinして、消えた主キーを検出する
3. 検出した主キーを`deleted_at`付きのtombstone行として流す
4. `hard_delete`ヒントが効いて、転送先の該当レコードが削除される

主キーだけを読めばいいので、`sql_table`の`table_adapter_callback`でカラムを絞れます。

```python
def only_pk(table):
    table._columns = [c for c in table._columns if c.name == "id"]
    return table
```

全件を読み直さずに削除を反映できて、しかも追加コストは実装の手間だけです。

Sling無償版にはこれができません。
設定がYAMLに閉じている以上、「主キーを突合して差分を出す」という処理を挟む場所がないからです。

もっとも、この方式には限界があります。
ある時点とある時点のスナップショット比較なので、**実行と実行の間に挿入されて削除された行は永久に観測されません**。
監査要件がある場合は、注意が必要です。

# MySQLのlog-based CDCは、OSSに存在しない

PK突合が力技すぎるならCDCを使いたくなりますが、MySQLだと選択肢が限られます。

dltのverified sourceでlog-basedのCDCが用意されているのは`pg_replication`、つまりPostgreSQL向けだけです。
MySQLのbinlogを読むソースは、(自力で探した限り)OSSに存在しません。

公式が推奨しているのは、Debeziumを`pydbzengine`で組み込む方式です。

https://dlthub.com/blog/debezium-and-dlt

とは言え、オフセットをファイルに保存して`engine.run()`で常駐させる構成なので、JavaベースのDebeziumを自前で運用することになります。
バッチで済ませたくて調べ始めたのに常駐プロセスが増えるのは、正直なところ本末転倒な気がします。

Sling側は、Pro Max($149/月)でbinlog CDCに対応しています。
しかも`sling run`のたびに1回処理してプロセスが終了する設計で、常駐するプロセスがありません。
cronやECS Scheduled Taskで回す前提になっていて、運用モデルとしては素直です。

- 初回はスナップショット開始**前**にbinlogの位置を記録してから全件取得する(スナップショットと初回増分の隙間を作らないため)
- 2回目以降は前回位置から再開し、最新位置まで読んで、新しい位置を保存する
- 位置の保存先は`SLING_STATE`で指定するstate store(進捗管理用のテーブルを別DBに持つ)

結局のところ、**MySQLでlog-based CDCをやるなら、どちらを選んでも無償では済みません**。
Sling Pro Maxを買うか、Debeziumを自前で抱えるかの二択です。

# 転送先が複数あるなら、S3 Tablesをハブにする手もある

ここまでは「MySQLから各転送先へ直接ロードする」前提で書いてきましたが、この構成だとRedshift用とSnowflake用でロードが二重に走ります。

代わりに[S3 Tables](https://aws.amazon.com/jp/s3/features/tables/)へ1回書いて、RedshiftとSnowflakeの両方からそれを読む構成も考えられます。
S3 Tablesは、Apache Iceberg形式のマネージドなテーブルバケットで、コンパクションやスナップショット管理を任せられます。

読み込み側の対応状況はこうなっていました。

| | Redshift | Snowflake |
|---|---|---|
| S3(Parquet) | Spectrumで外部テーブル | External Table |
| S3 Tables | **Glue Data Catalogとの統合が前提**。IAMロールを作成してクラスタにアタッチ | **2026年8月10日にGA**。Iceberg REST catalog統合 + catalog-linked database |

https://docs.snowflake.com/en/release-notes/2026/other/2026-08-10-amazon-s3-tables-iceberg-rest-catalog-integration-ga

Snowflakeは、一度カタログを繋いでおけば、**新しく登録されたテーブルが自動的に見えるようになります**。
テーブルを増やすたびにDDLを書かなくて済むのは楽そうです。

一方のRedshiftは、Glue Data Catalog経由でS3 Tablesを参照します。
`glue:GetCatalog`や`s3tables:GetTableBucket`を含むIAMポリシーを用意する必要があるので、初期セットアップは素のParquetより重いです。

https://docs.aws.amazon.com/redshift/latest/dg/querying-s3Tables.html

この構成が効いてくるのは、**Icebergなら行レベルのDELETEを表現できる**点です。
素のParquetは追記しかできないので、削除を反映しようとするとファイルごと書き直すことになります。
ここまで散々悩んできた物理削除の話が、フォーマットを変えるだけで素直に書けるようになります。

ただし、無償で完結するかは怪しくなります。

- **dlt**: コアのIcebergは「basic functionality」と明記されていて、高度な機能はdltHubチームが開発中。`catalog_type="s3tables-rest"`の設定例は**dlt Hub(商用)のドキュメント配下**にあります
- **Sling**: Icebergへの書き込みには対応していて、REST(S3 Tables含む)/ Glue / SQLの3カタログが使えます。ただし**有償ティアかどうかドキュメントに記載がありません**

あと、Snowflakeはposition deleteには対応しているものの、**equality deleteのファイルは読めない**という制約があります。
ELTツールがどちらの方式でDELETEを表現するかによっては、ここで詰まりそうです。

転送先が実質Redshiftだけなら、間にIcebergを挟む意味は薄いと思います。
カタログ統合の設定とS3 Tablesの料金が増えるだけです。
逆に複数の転送先へ配るなら、パイプラインが1本で済むぶん検討する価値はありそうです。

# 可逆な暗号化が必要だと、Slingには手段がない

個人情報の扱いで、Slingには明確な機能の欠落がありました。

Slingにはカラム単位で組み込み関数を適用する`transforms`があり、`hash_md5`と`hash_sha512`は無償で使えます。
PII対応の要望から実装された経緯があるようです。

```yaml
transforms:
  "*": [decode_utf16, replace_accents]
  col_sensitive: [hash_sha512]
```

ハッシュ化で足りるなら、これで終わりです。
問題は、**復号が必要な場合に使える関数が存在しない**ことでした。

`transforms`と式ベースのFunctions(v1.4.17+、こちらはPro)の両方を確認しましたが、`encrypt`/`decrypt`/AESに相当する関数がありません。
用意されているのは`hash()`と`hmac()`だけで、`hmac()`は鍵付きとはいえ一方向であることに変わりはありません。

`encode_base64`もありますが、これは暗号化ではありません。
可逆ではあるものの誰でもデコードできるので、個人情報の保護には使えません。

行単位で外部のトークン化APIを呼ぶ手段もありませんでした。
HTTP呼び出しができるHooksはストリームの前後に差し込むフックであって、行ごとの変換には使えません。

対してdltは、`add_map()`でリソースに任意のPython関数を挟めます。

```python
def encrypt_pii(doc):
    doc["email"] = aes_encrypt(doc["email"], key)
    return doc

resource = source.users.add_map(encrypt_pii)
```

中身は普通のPythonなので、AESで暗号化してもいいですし、外部のトークン化APIを呼んでもかまいません。
同じパイプラインのなかで完結します。

Slingでこれをやろうとすると、暗号化する仕組みを別に用意してS3などの中間領域に書き出し、そこからSlingでロードする2段構えになります。
そうなると「YAMLだけで完結する」というSling最大の利点が失われてしまいます。

# 暗号化したデータをSnowflakeでどう復号するか

ELT側で暗号化したなら、Snowflake側では復号の口が要ります。
ここはツール選定とは独立して重い話でした。

復号の実現方式は、鍵をどこに置くかで3つに割れます。

| | ① Snowflake内でENCRYPT/DECRYPT | ② 外部関数 + Lambda | ③ 外部ネットワークアクセス + Python UDF |
|---|---|---|---|
| 鍵の所在 | Snowflake内 | AWS(KMS) | AWS(KMS) |
| Snowflake Edition | Enterprise以上 | Enterprise以上 | Enterprise以上 |
| API Gateway | 不要 | 必須 | 不要 |
| Lambda | 不要 | 必要 | 不要にもできる |

①は手軽ですが、本番の個人情報保護には勧められません。
パスフレーズがクエリ履歴に残りますし、暗号文と鍵が同じ場所にあるのでSnowflake管理者は復号できてしまいます。
「生データを置かない」という目的が実質的に失われます。

②と③は鍵をAWS(KMS)で一元管理できるので、要件には合います。
トークン化ベンダーとの契約も不要で、Lambdaは自前で書けば済みます。

③は外部ネットワークアクセス(EAI)を使ってPython UDFから直接HTTPSを叩く方式で、API Gatewayを経由しません。
UDF内でKMSを直接呼べばLambdaも不要になるので、運用対象が2つ減ります。

ここで問題になるのが、②のコストです。

:::message alert
Snowflakeの24時間クエリ結果キャッシュは、外部関数を含むクエリでは無効になります。
:::

公式ドキュメントに「永続化されたクエリ結果は、クエリが外部関数を含まないことを要求する」と明記されています。
同じダッシュボードを開き直すたびに毎回Lambdaへのラウンドトリップが発生し、外部関数の実行には仮想ウェアハウスが必要なのでクレジットも毎回消費します。

救いは、マスキングポリシーの分岐で呼び出しを絞れることです。

```sql
CASE
  WHEN is_role_in_session('PII_VIEWER')
    THEN detokenize(val)     -- ここだけLambdaが呼ばれる
  ELSE val                   -- トークンのまま返す。呼び出しなし
END
```

大多数の分析ユーザーはトークンのまま扱い、平文が必要な一部のロールが見るときだけ呼び出しが発生する構成にできます。
逆に「担当者が管理画面で顧客一覧を常時開く」ような使われ方があると、コストと応答時間の両方に効いてきます。

あとLambda側の実装で、KMSの扱いには気をつけたほうが良さそうです。
毎回`kms:Decrypt`を呼ぶとKMSのAPI課金($0.03 / 1万リクエスト)が効いてきて、Lambda本体の呼び出し課金($0.20 / 100万リクエスト)より支配的になりがちです。
エンベロープ暗号化にして、データキーをLambda実行環境のグローバルスコープにキャッシュするのが定石です。

なお、③のEAI UDFでも結果キャッシュが無効になるのかはわかりませんでした。
外部関数については明文化されているものの、EAI UDFの扱いについては記載が見つかりません。

# Blue/Green切替でCDCが位置を見失わないか

Sling Pro MaxでCDCを使う場合、1つ気になる点があります。

Aurora MySQLのBlue/Green Deploymentで新しい環境を昇格すると、binlogのファイル名が`mysql-bin-changelog.000001`から振り直されます。
つまり、ファイル名とオフセットで位置を覚えている方式のブックマークは無意味になります。

しかも新しい番号は切替前の番号より小さくなるので、ツールによっては「まだ追いついていない」と誤認して無言でゼロ件を返し続ける可能性があります。
Airbyteでは実際に報告されています。

https://github.com/airbytehq/airbyte/issues/85783

GTID(グローバルトランザクションID)は切替後も引き継がれるので、これが唯一の手段になります。

SlingのGTID対応状況をドキュメントで調べた結果はこうでした。

| | 状況 |
|---|---|
| GTIDを記録している | ✅ ログにfile/offsetと並べて出力される |
| `replay_from`でGTID setを指定する | ✅ 可能 |
| 通常のresumeがGTIDベースか | ❓ 記載なし |
| state storeにGTIDを保存するか | ❓ 記載なし("current transaction log position"とだけ) |

MariaDB向けの説明に「transaction-boundary reads when resuming **by file/offset**」という記述があります。
ここから推測すると、既定はファイル名+オフセットベースの可能性が高そうです。
CDCはPro Maxのクローズド実装なので、ソースを読んで確かめられません。

ちなみにdltのcursorベース増分はbinlogに依存しないので、この問題の影響を構造的に受けません。
地味ですが、Blue/Greenを定期的に実施する環境では効いてくる差だと思います。

# 現時点の結論

机上調査の段階での判断はこうなりました。

**物理削除が発生しない、または論理削除に寄せられるなら、Sling無償版が最小コスト**です。
YAMLだけで完結しますし、バイナリ1つで動くので導入がいちばん楽です。
個人情報もハッシュ化で足りるなら`transforms`で済みます。

**物理削除への追従が必要で、かつ有償ライセンスを避けたいならdlt**です。
PK突合を自前で実装すれば無償で削除に追従できますし、`add_map()`があるので可逆な暗号化も同じパイプラインに書けます。
型の制御が細かくできるのも利点で、金額系のカラムがあるなら`pyarrow` backendを選べばDECIMALの精度が保たれます(既定の`sqlalchemy` backendより20〜30倍速いというおまけ付きです)。

**有償を許容するならSling Pro Max**が、CDCまで含めて最も素直です。
$149/月はチーム単位の定額で接続数もデータ量も無制限なので、レプリケーションインスタンスを立て続けるより安く収まる可能性はあります。
ただ、Blue/Greenの件が未確認なので、そこを確かめてからの判断になります。

**転送先が複数あるなら、S3 Tablesをハブにする構成**も候補に残ります。
Icebergなら削除を素直に表現できるので、ここまで悩んできた話がフォーマットの選択で片付く可能性があります。
ただし、両ツールともIceberg書き込みが無償の範囲かはっきりしないので、そこの確認が先です。

今回の要件に限って言えば、決め手になった2点はどちらも「Pythonで自分で書ける」というdltの性質から来ていました。
逆にSlingの利点である「YAMLだけで完結する」は、どちらの要件でも結局パイプラインの外に処理を持つ必要が出てくるので相殺されてしまいます。
